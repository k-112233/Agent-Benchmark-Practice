# Agent Evaluation：到底在评什么

## 1. 不是只看最后一句话

对终端型 Agent 来说，最终回复“我已经完成了”没有太大意义。真正需要检查的是环境最后变成了什么样。

例如任务要求生成 `result.json`，那么更可靠的证据是：

- 文件确实存在；
- JSON 能正常解析；
- 必需字段存在；
- 字段值符合题目要求。

而不是检查 Agent 的文本回复里有没有出现“完成”。

## 2. 我把评测信息分成三层

### 结果层

直接看任务目标有没有完成，例如文件、程序输出、数据库状态或测试结果。

### 过程层

记录执行过程中发生了什么，例如：

- 是否超时；
- 是否出现命令错误；
- 是否违反明确限制；
- 环境是否启动失败。

过程信息主要用来排查问题，通常不能代替最终结果检查。

### 汇总层

把很多 Trial 汇总起来，例如：

- 通过了多少次；
- 超时多少次；
- 平均运行时间；
- 哪类失败最多。

## 3. Verifier 是核心环节

Verifier 可以理解成“判卷程序”。一个好的 Verifier 要尽量做到：

1. 正确结果能通过；
2. 明显错误结果不能通过；
3. 重复运行时判定稳定；
4. 检查的是任务要求，而不是作者个人偏好的实现方式。

例如任务只要求输出正确 JSON，就不应该因为 Agent 使用了不同的代码结构而判错。

## 4. 为什么要重复运行

Agent 的执行可能具有随机性。同一个任务只跑一次，信息量很有限。

假设某个 Task 连续运行 5 次：

```text
pass
pass
fail
pass
timeout
```

这比单独说“它通过过一次”更有意义，因为你能同时看到稳定性和失败类型。

## 5. 失败不一定等于 Agent 不行

一次失败可能来自：

- 任务说明有歧义；
- 环境缺依赖；
- 网络或外部服务异常；
- Verifier 写错；
- 超时设置不合理；
- Agent 自己执行错误。

所以后面做失败分析时，第一步不是立刻修改 Prompt，而是先确认失败发生在哪一层。

## 6. 初学者可以先抓住一句话

**Agent Evaluation 评的是“在给定条件下，任务结果是否真的完成”，而不是 Agent 有没有说自己完成了。**
