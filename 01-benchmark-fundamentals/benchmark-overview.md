# Benchmark 基础：先把几个对象分清楚

## 1. Benchmark 在这里指什么

在 Agent Evaluation 场景里，Benchmark 不只是“一套题”。它通常还要规定任务怎么运行、结果怎么检查，以及多次运行以后怎样汇总结果。

先记住下面几个词就够用了：

| 术语 | 可以先这样理解 |
|---|---|
| Task | 一道需要 Agent 真正去完成的任务 |
| Agent | 执行任务的智能体或代理程序 |
| Environment | Agent 工作时所在的环境 |
| Trial | 某个 Agent 对某个 Task 的一次运行 |
| Verifier / Tests | 检查任务结果是否正确的程序 |
| Metrics | 把多次运行结果汇总成数字 |

## 2. 为什么它和普通问答不太一样

普通问答经常只看最后一句回答对不对。终端类 Agent 任务会多出一个完整的执行过程：

```text
读取任务说明
    ↓
查看环境和已有文件
    ↓
执行命令 / 修改文件 / 运行程序
    ↓
留下最终结果
    ↓
测试或 Verifier 检查结果
```

所以，一个任务能不能用于评测，不只看题目本身，还要看环境是否稳定、目标是否明确、结果是否能自动检查。

## 3. Task、Trial 和 Job 不要混在一起

### Task

Task 是“要做什么”。例如：

> 修改一个配置文件，使给定测试全部通过，同时不能改动指定输入文件。

### Trial

Trial 是“一次实际运行”。同一个 Task 可以运行多次，因为 Agent 的行为可能有随机性。

### Job

在 Harbor 这类评测框架里，一个 Job 可以组织一批 Trial。你可以把它理解成一次完整的评测作业。

初学时最容易混淆的是 Task 和 Trial：

```text
Task = 题目
Trial = 做这道题的一次记录
```

## 4. Environment 为什么重要

假设两台机器分别缺少不同的依赖，同一个 Agent 得到的结果可能完全不同。这时你看到的差异就不一定来自 Agent 能力，而可能来自环境。

因此，一个可用的 Benchmark 至少要尽量控制：

- 操作系统或基础镜像；
- 软件和依赖版本；
- 初始文件；
- 网络条件；
- 权限；
- 超时和资源限制。

## 5. 最小评测闭环

```text
Task
  ↓
Environment
  ↓
Agent 执行
  ↓
最终状态 / 输出文件
  ↓
Verifier / Tests
  ↓
Trial 结果
  ↓
Metrics
```

后面的章节基本都在补这条链路中的某一部分。

## 6. 可以先做的小练习

找一个最简单的文件处理任务，例如“把 `input.txt` 中的内容转成大写并写到 `output.txt`”。然后分别写出：

1. Task 是什么；
2. Environment 里需要哪些文件；
3. Agent 最后要留下什么；
4. Test 应该检查什么。

如果这四项能说清楚，就已经进入 Agent Benchmark 的基本思路了。
