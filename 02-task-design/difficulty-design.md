# Difficulty Design

## 1. 难度不是“让任务更麻烦”

Benchmark Task 的难度应尽量来自问题本身，而不是来自不必要的障碍。

较合理的难度来源包括：

- 多步骤推理；
- 多文件依赖；
- 状态追踪；
- 错误定位；
- 工具选择；
- 约束下的修改；
- 对结果进行验证。

不合理的难度来源包括：

- 故意隐藏必要信息；
- 无意义的大量文件；
- 模糊成功标准；
- 随机破坏环境；
- 与任务目标无关的格式陷阱。

## 2. Solvability 优先

一个 Task 在讨论“难不难”之前，首先必须“能不能解”。

至少应确认：

- 输入完整；
- 环境可运行；
- 依赖可获得；
- 任务说明没有自相矛盾；
- 成功目标真实可达到；
- Verifier 可以识别正确解。

## 3. 一个简单难度框架

### Easy

特点：

- 单步骤或少量步骤；
- 目标直接；
- 文件和依赖少；
- 错误位置明显。

### Medium

特点：

- 需要跨文件理解；
- 需要若干操作步骤；
- 存在约束；
- 需要运行测试并迭代修复。

### Hard

特点：

- 较长执行链；
- 多个中间状态；
- 需要定位非显式错误；
- 多种工具协同；
- 需要处理复杂约束。

这只是学习项目中的粗略分级，不是官方标准。

## 4. 难度校准

不能只凭作者主观判断难度。

更合理的流程：

```text
设计任务
  ↓
人工 / Oracle 验证可解性
  ↓
运行多个 Agent / 多次 Trial
  ↓
观察通过率与失败模式
  ↓
判断任务是否过易、过难或不稳定
  ↓
修改并重新验证
```

如果所有强 Agent 都轻易通过，任务可能过于简单。

如果人工可解但 Agent 经常在真正有挑战性的环节失败，可能说明难度有效。

如果所有 Agent 都因为环境错误或说明歧义失败，则不是“高质量难题”。

## 5. Hard for the Right Reasons

可以用一句问题进行检查：

> Agent 失败，是因为它缺乏解决任务所需的能力，还是因为任务本身设计得不稳定？

只有前者更接近有效 Benchmark 难度。

## 6. 迭代设计

任务难度通常不是一次确定的。

常见迭代过程：

```text
v1: 太简单
↓
增加真正必要的推理或操作
v2: 出现歧义
↓
修正说明
v3: Verifier 过严
↓
放宽不必要限制
v4: 可解、稳定、具有区分度
```

因此，Task Design 本质上也是一个测试和校准过程。
