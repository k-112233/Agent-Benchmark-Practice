# Task Abstraction

## 1. 从需求描述到可执行任务

真实需求通常不是天然适合 Benchmark 的。

例如：

> “把这个项目修好。”

这句话无法直接用于稳定评测，因为没有说明：

- 什么叫“修好”；
- 当前状态是什么；
- 可以改什么；
- 不可以改什么；
- 最后怎样判断成功。

Task Abstraction 的目的，是把模糊需求转化为可执行、可验证结构。

## 2. 六个核心要素

### 1. Input

任务提供给 Agent 的信息，例如：

- 文件；
- 数据；
-代码；
- 配置；
- 文本要求。

### 2. Initial State

开始执行时环境处于什么状态。

例如：

```text
project/
├── app.py
├── config.json
└── tests/
```

并明确已有错误或缺陷。

### 3. Target State

任务完成后应达到什么状态。

例如：

- 所有指定测试通过；
- 目标文件生成；
- 配置值符合要求；
- 输出满足 schema。

### 4. Action Space

Agent 可以进行哪些操作，例如：

- 读取和修改文件；
- 执行 Shell 命令；
- 安装允许的依赖；
- 运行测试。

### 5. Constraints

限制条件，例如：

- 不得修改某文件；
- 不得访问网络；
- 不得改变公共接口；
- 必须在给定目录完成；
- 必须在时间预算内结束。

### 6. Evidence

如何证明任务已经完成。

例如：

- 单元测试；
- 文件内容；
- 命令退出码；
- 结构化输出；
- 状态检查。

## 3. 抽象模板

一个通用学习模板：

```text
Input:
    Agent 能看到什么？

Initial State:
    环境一开始是什么状态？

Target State:
    最后必须达到什么结果？

Action Space:
    Agent 能做什么？

Constraints:
    Agent 不能做什么？

Evidence:
    怎样客观确认完成？
```

## 4. 为什么 Evidence 很重要

如果 Target State 无法被 Evidence 客观验证，任务就难以稳定评测。

例如：

> “让代码更优雅。”

这是一个弱目标。

改成：

> “在不改变公开接口的情况下，使指定测试全部通过，并满足静态检查要求。”

就更容易形成可验证任务。

## 5. 抽象不是增加复杂度

好的 Task Abstraction 应减少无关细节。

难度应来自真正需要解决的问题，而不是：

- 隐藏关键信息；
- 人为制造文件噪声；
- 使用不必要的限制；
- 依赖猜测评测者意图。

> 本项目后续的任务规范和难度设计都建立在这一抽象框架之上。
