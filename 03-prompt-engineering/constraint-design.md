# Constraint Design：限制要具体，也要有必要

## 1. 为什么任务需要约束

开放式要求可能有很多种完成方式。约束的作用是明确边界，而不是把 Prompt 写得越长越好。

约束太少，Agent 容易做出题目没打算接受的结果；约束太多或互相冲突，又会让任务变成“猜作者想法”。

## 2. 常见约束

| 类型 | 例子 | 可以怎样检查 |
|---|---|---|
| 文件结构 | 必须生成指定文件 | 检查路径 |
| 格式 | 输出必须是合法 JSON | 尝试解析 |
| 路径 | 结果写入指定目录 | 检查输出位置 |
| 行为 | 不能修改输入文件 | 比较文件哈希或内容 |
| 资源 | 运行时间不能超过上限 | 记录 runtime |
| 网络 | 禁止联网 | 环境或网络策略 |

## 3. 区分“必须”和“最好”

例如：

- **硬约束**：违反就算任务失败；
- **偏好**：最好满足，但不应该单独导致任务失败；
- **背景信息**：只是帮助理解。

如果把所有偏好都写成硬约束，Verifier 很容易变得过严。

## 4. 每个关键约束都问两个问题

1. Agent 能不能从说明里看懂？
2. 最后能不能检查？

例如：

> 输出格式必须正确。

不如写成：

> `result.json` 必须能被 JSON 解析器读取，且顶层包含 `records` 数组。

后者可以直接写测试。

## 5. 常见问题

- Prompt 提了要求，但测试完全不检查；
- 测试检查了 Prompt 没写的条件；
- 两条硬约束互相冲突；
- 禁止事项写了很多，却没说正确结果是什么；
- 用“规范”“合理”“完整”等词代替具体标准。

设计约束时，我更倾向于“少而清楚”：只保留真正影响任务结果的限制。
