# Constraint Design

## 1. 为什么需要约束

模型可能对开放式要求作出多种解释。约束设计的目标是缩小不必要的解释空间，使输出符合任务目标、运行环境和交付要求。

约束过少容易造成输出不一致；约束过多或互相冲突，则可能使任务无法完成。

## 2. 常见约束类别

| 类别 | 约束示例 | 可检查方式 |
|---|---|---|
| 结构约束 | 必须包含指定目录和文件 | 文件系统检查 |
| 格式约束 | 配置文件必须是合法 TOML | 解析器检查 |
| 技术约束 | 使用指定语言或运行时 | 代码与环境检查 |
| 路径约束 | 产物写入指定目录 | 路径检查 |
| 行为约束 | 不得修改指定输入文件 | 哈希或内容比较 |
| 资源约束 | 执行时间不得超过上限 | 运行时统计 |
| 安全约束 | 不得读取或输出凭据 | 代码审查与隔离检查 |

## 3. 约束优先级

- **硬约束**：违反即意味着结果不符合要求。
- **软约束**：尽量满足，但在冲突时允许权衡。
- **背景信息**：帮助理解问题，不直接构成验收条件。

如果多个硬约束相互冲突，应先修正任务定义，而不是要求模型自行猜测优先级。

## 4. 约束可测试性

每个关键约束都应回答两个问题：

1. 模型能否从指令和环境中理解它？
2. 完成后能否通过明确证据检查它？

例如，“输出必须合法”过于宽泛；“输出文件必须能被 JSON 解析器解析，且顶层必须包含 `records` 数组”则更容易验证。

## 5. 常见问题

- 约束只出现在提示词里，却没有对应检查。
- 验证器检查了提示词从未提出的条件。
- 多条约束互相矛盾。
- 把建议性要求写成硬性要求。
- 只描述禁止事项，没有说明期望的正确结果。
