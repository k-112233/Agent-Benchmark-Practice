# Iterative Prompt Refinement

## 1. 迭代的基本逻辑

Prompt 优化不是简单地不断增加文字，而是基于可观察的失败证据，定位问题并修改相关指令。

基本闭环：

1. 明确当前 Prompt 版本。
2. 运行模型并保存输入、输出和运行条件。
3. 使用测试或检查项识别失败。
4. 将失败归类为指令、任务定义、环境、生成内容或验证器问题。
5. 选择一个主要原因进行修改。
6. 使用相同或可比较的条件重新运行。
7. 比较修改前后的结果，并记录是否引入新的问题。

## 2. 失败归因

| 失败类型 | 典型现象 | 优先检查方向 |
|---|---|---|
| 目标理解偏差 | 输出完成了相近但不同的目标 | Objective 是否明确 |
| 约束遗漏 | 忽略路径、格式或禁止事项 | 约束是否显式且突出 |
| 结构不完整 | 缺文件、目录或配置项 | 是否给出文件清单 |
| 内容错误 | 文件存在但逻辑不正确 | 示例、上下文和质量标准 |
| 环境失败 | 依赖缺失、命令无法执行 | 环境配置与运行条件 |
| 验证器问题 | 正确产物未通过或错误产物通过 | 测试逻辑和判定边界 |

失败现象不等于根本原因。例如测试失败可能由任务指令、模型生成内容、环境配置或测试本身造成，不能未经检查就归因于 Prompt。

## 3. 控制变量

为了判断一次 Prompt 修改是否有效，应尽量保持其他条件一致：

- 使用相同任务版本。
- 保持模型和模型参数一致。
- 保持环境与依赖版本一致。
- 保持测试和通过标准一致。
- 记录尝试次数和异常运行。

如果一次同时修改 Prompt、环境、测试和任务目标，就很难判断结果变化来自哪里。

## 4. 版本记录模板

| 字段 | 记录内容 |
|---|---|
| Prompt Version | 版本号或 Git commit |
| Change | 本次修改内容 |
| Failure Evidence | 修改前的失败证据 |
| Hypothesis | 预计解决的问题 |
| Test Condition | 模型、任务和环境版本 |
| Result | 修改后的测试结果 |
| Regression | 是否出现新的失败 |

## 5. 迭代原则

- 优先修复明确、可复现的问题。
- 每次修改尽量聚焦一个原因。
- 不因单次成功就认定问题彻底解决。
- 不通过削弱验收标准掩盖任务缺陷。
- 保留失败记录，避免重复试错。
- 当根因不在 Prompt 时，应修改任务定义、环境或验证器，而不是继续堆叠提示词。

## 6. 隐私与数据边界

真实工作中的 Prompt、客户要求、任务描述和内部验收规则可能属于非公开资料。本仓库只使用独立编写的通用示例，不复制内部提示词或将其改写后公开。
