# Iterative Refinement：根据失败改，不要靠感觉一直加 Prompt

## 1. 一个简单迭代闭环

Prompt 修改最好由实际失败推动：

```text
保存当前版本
    ↓
运行任务
    ↓
看测试和日志
    ↓
判断失败原因
    ↓
只修改相关部分
    ↓
重新运行
```

如果每次都同时改 Prompt、环境和测试，最后即使成功，也很难知道到底是哪一项起作用。

## 2. 先分清失败属于哪一类

| 现象 | 优先检查 |
|---|---|
| 做了相近但不是要求的事 | 目标是否写清楚 |
| 忽略路径或格式 | 约束是否明确 |
| 少文件、少配置项 | 是否给出结构清单 |
| 代码逻辑错误 | 上下文、示例和任务本身 |
| 命令跑不起来 | 环境和依赖 |
| 正确结果也被判错 | Verifier / Tests |

“测试失败”只是一种现象，不代表一定是 Prompt 有问题。

## 3. 尽量控制变量

为了比较修改前后是否真的改善，尽量保持：

- Task 版本一致；
- 模型和主要参数一致；
- 环境一致；
- 测试一致；
- 超时一致。

## 4. 记录什么就够用了

不需要复杂系统，一个小表格就能避免反复试错：

| 字段 | 示例 |
|---|---|
| Version | v3 |
| Problem | 输出路径错误 |
| Evidence | Test 2 找不到文件 |
| Change | 明确写出输出绝对路径 |
| Result | 4/4 tests passed |
| Regression | 未发现 |

## 5. 不要为了通过测试降低正确标准

如果任务本来要求三个关键结果，不能因为模型经常只完成两个，就把第三个测试删掉。

正确做法是先确认：

- 第三个要求是否合理；
- 说明是否写清楚；
- 环境是否支持；
- Verifier 是否准确。

确认没问题后，再判断 Agent 是否真的没有完成。

## 6. 公开练习时的资料来源

本仓库的例子只使用公开资料、自建任务和合成数据。遇到来源或授权不明确的材料，先不要放进公开仓库。
