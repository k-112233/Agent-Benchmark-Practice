# 可复现环境：让任务在不同运行中保持一致

## 1. 什么是可复现

可复现环境（Reproducible Environment）是指：在明确的输入、配置和依赖条件下，任务能够在重新构建或重新运行时得到可解释、可比较的结果。

对 Agent 评测而言，可复现不仅是“容器能启动”，还包括：

- 运行环境和依赖版本明确；
- 初始数据和文件状态明确；
- 执行入口和参数明确；
- 外部依赖与网络条件明确；
- 验证逻辑和结果记录明确。

如果这些条件不受控，任务结果的变化就可能来自环境差异，而不一定来自 Agent 能力差异。

## 2. 环境中需要固定和记录的内容

### 2.1 基础镜像与运行时版本

尽量使用明确的镜像标签和软件版本，避免依赖含义会变化的模糊标签。对于要求严格复现的场景，可以记录镜像 digest，而不只记录可变标签。

示例：

```dockerfile
FROM python:3.12.3-slim
```

说明：标签本身仍可能对应更新后的镜像内容；高要求场景应进一步记录实际镜像 digest。

### 2.2 依赖版本

避免只写不受约束的依赖：

```text
requests
pytest
```

练习项目可以使用固定版本：

```text
requests==2.32.3
pytest==8.3.5
```

版本固定能减少依赖漂移，但不代表跨操作系统、处理器架构和系统库环境必然完全一致。必要时还要记录 Python 版本、系统依赖和平台信息。

### 2.3 输入数据和初始状态

需要明确：

- 输入文件的来源和版本；
- 文件编码、换行符和目录结构；
- 初始数据库或状态文件；
- 随机数种子（如果任务使用随机过程）；
- 是否存在任务之间共享或残留的状态。

用于公开练习时，优先使用自行生成的合成数据，并记录生成方法。

### 2.4 网络和外部服务

网络访问会引入额外的不确定性，例如下载内容变化、服务不可用、API 限流和凭据失效。

任务设计应明确：

- 是否允许联网；
- 访问哪些服务；
- 是否需要外部凭据；
- 外部资源是否固定版本或有缓存；
- 网络失败时应如何判定。

不要把个人令牌、账号密码或内部服务地址写进仓库。

## 3. 环境描述清单

建议为每个练习项目维护一份环境说明，至少包括：

| 项目 | 应记录的信息 |
|---|---|
| 操作系统 | 发行版或基础镜像 |
| 架构 | 例如 x86_64 / ARM64 |
| 运行时 | Python、Node.js 等版本 |
| 依赖 | 包名与版本 |
| 构建方式 | Dockerfile 和构建命令 |
| 启动方式 | 完整命令及参数 |
| 输入 | 文件、数据版本、初始状态 |
| 网络 | 是否联网、外部依赖 |
| 输出 | 预期产物和保存位置 |
| 验证 | 测试命令、判定标准 |

记录环境信息的目的不是堆砌配置，而是让其他人能够按说明重建并理解执行条件。

## 4. 隔离与状态管理

### 4.1 每轮运行使用干净状态

如果一次运行会修改文件、数据库或缓存，下一轮运行前应恢复初始状态。否则后续结果可能受到前一轮残留影响。

常见做法：

- 每轮创建新的容器；
- 使用独立工作目录；
- 每次运行前重置测试数据；
- 将运行产物写入独立目录；
- 不在多轮实验间复用未经清理的状态。

### 4.2 区分输入、工作区和输出

一种清晰的目录划分方式：

```text
workspace/
├── input/       # 运行前提供的输入
├── work/        # 执行过程中的可变文件
├── output/      # 需要检查或保留的产物
└── logs/        # 执行日志
```

这只是练习项目的组织示例，不是 Terminal-Bench 或 Harbor 的强制目录规范。

### 4.3 避免隐藏依赖

常见隐藏依赖包括：

- 只在开发者电脑上安装的软件；
- 未记录的环境变量；
- 依赖用户主目录中的配置文件；
- 依赖当前工作目录；
- 依赖未固定版本的在线资源；
- 依赖前一次运行留下的文件。

发现隐藏依赖后，应将其显式化、固定化，或从任务设计中移除。

## 5. 可复现性检查流程

按以下顺序执行，能较快定位问题：

1. **确认输入**：检查文件是否齐全、内容是否符合预期。
2. **确认环境**：核对镜像、运行时和依赖版本。
3. **确认启动入口**：使用文档中记录的命令启动。
4. **确认初始状态**：清理上一次运行产生的状态。
5. **执行任务**：记录命令、参数和运行时间。
6. **执行验证**：使用固定测试命令和明确判定标准。
7. **保存证据**：保存必要日志、版本信息和结果摘要。
8. **重复运行**：至少进行一次干净环境下的重复执行，观察结果是否一致。

如果结果不一致，先比较环境、输入和状态，再检查任务本身及验证逻辑。

## 6. 常见的可复现性问题

| 问题 | 可能原因 | 改进方向 |
|---|---|---|
| 同一任务多次结果不同 | 随机性、残留状态、时间依赖 | 固定随机种子、重置状态、明确时间条件 |
| 不同机器表现不同 | 系统库、架构、路径或权限差异 | 固定基础环境并记录平台 |
| 依赖安装结果不同 | 依赖版本未固定、包源变化 | 固定版本并记录依赖清单 |
| 任务偶发失败 | 网络、外部服务或资源竞争 | 明确外部依赖，区分环境故障与任务失败 |
| 测试通过但交付不完整 | 验证只覆盖运行结果，未检查文件结构 | 增加文件、路径和交付完整性检查 |

## 7. 本章练习

创建一个完全自建的简单任务：

1. 编写 Dockerfile，固定基础运行时版本。
2. 准备一个简单输入文件和一个执行脚本。
3. 将输入、工作目录和输出目录分开。
4. 编写一个自动检查输出是否符合预期的测试。
5. 连续运行两次，每次从干净状态开始。
6. 记录两次运行的环境信息和结果，分析是否一致。

练习报告可按以下结构整理：

```text
任务目标：
环境版本：
输入与初始状态：
构建命令：
运行命令：
验证命令：
第一次运行结果：
第二次运行结果：
差异与原因分析：
```

## 8. 与 Agent 评测的关系

当 Agent 在容器中执行任务时，环境是实验条件的一部分。若环境配置不明确，评测结果就可能混合 Agent 能力、环境可用性和外部服务状态等因素。

因此，环境复现与任务设计、测试设计、失败分析应形成闭环：

- 任务设计明确初始状态和目标状态；
- 环境配置保证初始条件可重建；
- 执行过程记录必要证据；
- 测试逻辑验证目标状态；
- 失败分析区分 Agent 错误、任务歧义和环境问题。
