# 可复现环境：为什么“我电脑上能跑”还不够

## 1. 什么叫可复现

这里的“可复现”不是要求每次运行的每个细节都一模一样，而是希望在明确的输入、环境和配置下，重新运行时得到可解释、可比较的结果。

对 Agent 评测来说，至少需要知道：

- 用了什么运行环境；
- 依赖是什么版本；
- 初始文件是什么；
- 启动命令是什么；
- 是否联网；
- 最后怎样验证。

如果这些条件不断变化，就很难判断结果差异到底来自 Agent 还是环境。

## 2. 哪些东西最好固定下来

### 基础镜像和运行时

练习时尽量避免：

```dockerfile
FROM python:latest
```

更明确一些：

```dockerfile
FROM python:3.12.3-slim
```

标签仍可能发生变化；要求更严格时还可以记录镜像 digest。

### Python 依赖

不固定版本：

```text
requests
pytest
```

固定版本：

```text
requests==2.32.3
pytest==8.3.5
```

固定依赖能减少版本漂移，但还要注意操作系统和系统库差异。

### 输入和初始状态

需要明确：

- 输入文件版本；
- 文件编码；
- 目录结构；
- 随机种子（如果有随机过程）；
- 上一次运行是否留下缓存或输出。

## 3. 网络是常见的不稳定来源

联网任务可能遇到：

- 下载内容更新；
- 服务暂时不可用；
- API 限流；
- 凭据过期；
- DNS 或网络波动。

因此任务最好明确“允许访问什么、什么时候需要网络”。如果能把固定资源提前放进环境，通常更容易复现。

## 4. 每轮运行尽量从干净状态开始

假设第一次运行生成了 `cache.json`，第二次直接复用这个文件，那么两次 Trial 的初始条件已经不一样了。

常见做法：

- 每轮创建新容器；
- 每轮使用独立工作目录；
- 运行前重置测试数据；
- 输出写入独立目录；
- 不复用上一次留下的临时状态。

## 5. 一个容易理解的目录划分

```text
workspace/
├── input/      # 原始输入
├── work/       # 执行过程中允许修改
├── output/     # 最终要检查的结果
└── logs/       # 必要日志
```

这只是练习时的一种组织方法，不是 Harbor 或 Terminal-Bench 的固定目录格式。

## 6. 隐藏依赖很容易被忽略

常见隐藏依赖：

- 只有开发者电脑上安装的软件；
- 没写进文档的环境变量；
- 用户主目录里的配置；
- 当前工作目录；
- 未固定版本的在线文件；
- 上一轮留下的缓存。

一旦发现，就应该把它显式写出来、固定下来，或者从任务中移除。

## 7. 一个实用的复现检查顺序

1. 检查输入文件；
2. 检查镜像、运行时和依赖版本；
3. 按文档里的命令启动；
4. 清理上一次运行状态；
5. 执行任务；
6. 执行固定测试；
7. 保存必要的版本和结果信息；
8. 在干净环境再跑一次。

如果两次结果不同，先比较环境和初始状态，再怀疑 Agent 本身。

## 8. 一个练习记录模板

```text
任务目标：
基础镜像：
Python 版本：
依赖版本：
输入文件：
构建命令：
运行命令：
验证命令：
第一次结果：
第二次结果：
差异：
```

## 9. 与后面章节的关系

可复现环境会直接影响：

- Test 是否稳定；
- Verifier 是否可靠；
- 多次 Trial 能不能比较；
- Failure Analysis 能不能正确归因。

因此它不是单独的 Docker 技巧，而是评测设计的一部分。
