# 失败分析：从结果异常定位真正原因

## 1. 为什么需要失败分析

评测失败是观察结果，不是原因本身。一次 Trial 失败，可能来自 Agent 决策、任务说明、环境配置、外部依赖、超时或 Verifier 缺陷。

如果不区分原因就直接修改提示词，容易把问题修在错误位置，也可能引入新的变量。

## 2. 建立统一的失败分类

| 类别 | 说明 | 典型证据 |
|---|---|---|
| Instruction / Specification | 任务目标不清或存在冲突 | 不同理解都看似合理 |
| Agent Execution | Agent 操作错误或未完成目标 | 轨迹显示错误操作或遗漏 |
| Environment | 环境或依赖异常 | 构建日志、命令错误、权限问题 |
| Timeout | 超出时间限制 | 超时记录、执行轨迹中断 |
| Verifier | 测试逻辑或验证环境异常 | 正确结果仍失败、reward 未生成 |
| External Dependency | 网络或外部服务异常 | 请求失败、服务不可用 |
| Invalid Run | 试验未有效完成 | 启动失败、记录不完整 |

分类定义应保持清晰，避免同一问题被随意归入不同类别。

## 3. 证据优先的排查流程

1. **确认阶段**：区分环境构建、Agent 启动、任务执行、Verifier 执行和结果解析阶段。
2. **检查结构化结果**：查看 Trial 状态、耗时、退出码、reward 和测试报告。
3. **阅读关键日志和轨迹**：寻找第一个异常，而不是只关注最后一条错误信息。
4. **复现问题**：在相同输入和环境下重复运行。
5. **提出可验证的原因假设**：例如“失败是由于输入路径不一致造成的”，再只修改路径或相关配置。
6. **回归测试**：修复后重新执行原失败用例，并检查相邻用例是否受到影响。

## 4. 区分 Agent 错误与任务/测试错误

- 参考解法也无法通过：优先检查任务环境、任务说明和 Verifier。
- 多个 Agent 在同一位置以相似方式失败：检查任务是否存在歧义或环境障碍。
- 正确输出被判定失败：检查 Verifier 的预期值、路径、编码和容差。
- 结果时好时坏：检查随机性、时间依赖、网络和残留状态。
- Agent 运行结束但没有验证结果：检查测试脚本执行和 reward 输出流程。

这些信号只是排查方向，不能单独作为最终归因。

## 5. 迭代时控制变量

一次迭代尽量只改变一个主要因素，例如只修改任务说明、环境依赖、测试逻辑或超时配置。如果同时修改多个因素，即使结果改善，也难以判断真正起作用的是哪项变化。

建议维护变更记录：

```text
版本：
观察到的问题：
证据：
原因假设：
本次修改：
预期变化：
实际结果：
是否回归通过：
```

## 6. 失败分析案例（合成示例）

现象：Agent 生成结果文件，但 Verifier 判定失败。

1. 检查文件，确认文件存在。
2. 检查内容，发现末尾多了一个换行符。
3. 检查测试，发现测试使用严格字节比较。
4. 回看任务说明，发现只要求文本内容，没有规定必须禁止末尾换行。
5. 判断测试条件可能超出了任务说明。
6. 将验证逻辑调整为符合已声明要求的内容比较，并增加正反例回归测试。

这类失败不应直接归因为 Agent 未完成任务；需要先判断测试是否准确表达任务要求。

## 7. 本章练习

准备 5 条合成失败记录，分别模拟任务说明歧义、Agent 操作错误、环境依赖缺失、Verifier 误判和执行超时。对每条记录填写发生阶段、证据、初步分类、原因假设和下一步验证动作。
