# Failure Analysis：失败以后先找发生在哪一层

## 1. “失败”只是结果，不是原因

一次 Trial 没通过，可能是：

- Agent 做错了；
- Task 写得不清楚；
- Environment 出问题；
- 超时；
- Verifier 写错；
- 外部服务失败。

如果没分清原因就一直改 Prompt，很容易修错地方。

## 2. 先做一个简单分类

| 类别 | 常见现象 |
|---|---|
| Task / Instruction | 不同理解都说得通 |
| Agent Execution | 操作错误、遗漏步骤 |
| Environment | 依赖、权限、路径出错 |
| Timeout | 到时间还没完成 |
| Verifier | 正确结果也被判错 |
| External Dependency | 网络或服务异常 |
| Invalid Run | 运行根本没有正常开始或记录不完整 |

## 3. 排查顺序

我更习惯从“最早出现异常的位置”开始：

1. 环境有没有成功启动；
2. Agent 有没有正常开始；
3. 任务执行到哪一步出错；
4. 最终结果文件是否存在；
5. Verifier 有没有正常执行；
6. 最后的 status 是怎样生成的。

不要只看最后一行报错，因为最后一行往往只是前面问题的结果。

## 4. 几个常见判断信号

### 参考解法也过不了

先查 Task、Environment 和 Verifier，不要先怪 Agent。

### 多个 Agent 都卡在同一个奇怪位置

可能是任务说明、路径或环境有共同问题。

### 正确输出被判失败

查 Verifier 的预期值、编码、路径和容差。

### 同一个任务时好时坏

查随机性、网络、时间依赖和残留状态。

这些只是线索，最终归因还要靠实际证据。

## 5. 修改时尽量一次只动一个主要因素

例如先只改任务说明，重新跑；或者只修测试，再跑。

如果 Prompt、Dockerfile、Test 和 timeout 一起改，即使结果变好，也很难知道哪一项真正解决了问题。

## 6. 一个合成例子

任务要求输出文本 `hello`，Agent 生成的文件内容是：

```text
hello\n
```

Verifier 用字节级完全相等比较，判定失败。

这时要回到任务说明看：题目有没有明确禁止末尾换行？

如果没有，那么问题可能在 Test 过严，而不一定是 Agent 错。

## 7. 简单记录模板

```text
问题现象：
最早异常位置：
已有证据：
初步分类：
原因假设：
本次只修改什么：
重新运行结果：
```

能把这几项写清楚，失败分析就已经比“不断重试”有效很多。
