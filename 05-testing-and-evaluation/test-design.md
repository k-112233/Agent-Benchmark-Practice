# Test Design：把“完成了”变成可以检查的证据

## 1. 测试先对应任务要求

任务说明负责说“要做什么”，Test 负责检查“最后到底有没有做到”。

最简单的办法是做一张对应表：

| 任务要求 | 可观察结果 | 测试方法 |
|---|---|---|
| 创建指定文件 | 文件存在 | 检查路径 |
| 写入指定内容 | 文件内容 | 读取并比较 |
| 输出 JSON | 结构化文件 | 解析字段和类型 |
| 实现函数 | 程序行为 | 给输入并检查输出 |
| 保留原文件 | 文件未变化 | 比较内容或哈希 |

这张表很有用，因为它能同时发现“要求没测到”和“测试超出了要求”。

## 2. 常见的测试层次

### 文件和结构

检查文件是否存在、目录是否正确、格式能不能解析。

### 内容和数据

检查文本、JSON、CSV、数值和字段类型。

### 程序行为

真正运行程序，检查输入和输出，而不是只看源代码中有没有某个字符串。

### 边界情况

例如空输入、缺文件、非法格式、重复数据和极端数值。

## 3. 一个最小例子

任务要求：在 `/workspace/result.txt` 写入 `completed`。

```python
from pathlib import Path


def test_result_file_exists():
    path = Path("/workspace/result.txt")
    assert path.is_file()


def test_result_content():
    path = Path("/workspace/result.txt")
    assert path.read_text(encoding="utf-8").strip() == "completed"
```

这里没有检查 Agent 用了 `echo` 还是 Python，因为“用哪条命令”不是任务目标。

## 4. 一个好测试至少应该满足

- **相关**：对应明确要求；
- **够用**：关键要求没有漏掉；
- **稳定**：同样输入下不会随机变结果；
- **好定位**：失败后知道是哪一项出问题；
- **不过度限制实现**：不同正确做法都能通过；
- **不只看表面特征**：尽量检查真实行为。

Terminal-Bench 当前公开指南特别强调结果可验证，而且 verifier 应可靠、稳定。

## 5. 测试失败时先别急着怪 Agent

可能的原因包括：

- Agent 真没完成；
- 任务说明有歧义；
- 环境出错；
- Test 自己写错；
- Test 检查了说明里没要求的东西；
- 超时导致结果不完整。

后面的 Failure Analysis 会专门处理这个问题。

## 6. 动手练习

1. 自己写一个很小的文件处理任务；
2. 列 3 条明确要求；
3. 每条要求写一个 Test；
4. 准备一个正确结果和两个错误结果；
5. 看测试是否能正确区分。

如果错误结果也通过，说明 Test 太松；如果正确结果失败，说明 Test 可能太严或任务说明不完整。
