# Verifier 设计：可靠地判断任务是否完成

## 1. Verifier 是什么

Verifier（验证器）是评测流程中负责检查任务结果并输出判定的组件，通常由测试脚本、测试代码和必要依赖构成。

在 Harbor 的任务结构中，测试通常放在 `tests/` 目录，由测试脚本执行；验证结果通过框架约定的 reward 文件等形式交给评测框架读取。具体路径和格式应以所使用框架版本的文档为准。

Verifier 的职责是判断任务目标是否达到，而不是复盘 Agent 的全部操作。

## 2. 设计原则

### 对齐任务说明
每项关键检查都应能在任务说明中找到依据。反过来，任务说明中的关键要求也应有对应验证。若出现“任务没说、测试却要求”，应先判断是说明缺失还是测试越界。

### 验证结果，而不是表面痕迹
优先检查文件或数据的实际内容、程序在给定输入下的行为、关键状态变化，以及输出结构和约束。谨慎使用只检查关键词、文件名、注释或代码结构的方式。

### 控制验证器可见信息
如果任务要求 Agent 独立完成工作，测试答案或参考解决方案不应意外暴露给 Agent。测试环境、文件挂载和权限设计应避免 Agent 直接修改验证逻辑或伪造判定结果。具体隔离方式取决于评测框架和任务配置。

### 结果明确且可解释
Verifier 应产生明确的成功、失败或错误状态。失败信息应尽量指出具体检查点。

## 3. Reward 与测试报告

某些评测框架使用 reward 值概括任务是否通过，并通过约定文件传递判定结果。具体文件路径和格式应按框架版本与配置确认。

需要区分：
- **Reward**：概括一次试验是否达到成功标准。
- **Test report**：记录各项测试的通过、失败和错误情况。
- **Logs**：帮助定位执行和验证过程中的问题。

只保留总分会丢失诊断信息。练习项目可同时输出总判定和逐项测试结果。

## 4. Verifier 的测试方法

1. **正向检查**：准备符合任务要求的结果，确认 Verifier 判定通过。
2. **负向检查**：准备缺文件、错误内容或行为错误的结果，确认 Verifier 判定失败。
3. **重复运行**：在相同初始状态下多次运行，观察结果是否稳定。
4. **验证器异常检查**：检查依赖缺失、路径错误、权限问题、超时和 reward 文件缺失。

验证器自身异常应与 Agent 未完成任务区分。

## 5. 常见设计缺陷

| 缺陷 | 后果 | 改进 |
|---|---|---|
| 只检查文件存在 | 空文件也可能通过 | 检查内容和实际行为 |
| 只检查关键词 | 容易被表面修改绕过 | 执行程序并验证输出 |
| 测试未声明要求 | 不公平失败 | 对齐任务说明 |
| 依赖随机输出 | 结果不稳定 | 固定随机种子或使用容差 |
| 依赖外部网络 | 受服务状态影响 | 固定资源或明确网络条件 |
| 测试错误算作 Agent 失败 | 评测结论失真 | 独立记录 verifier error |
| Agent 可篡改测试 | 判定可信度下降 | 合理隔离测试和执行权限 |

## 6. 本章练习

为自建文件处理任务实现 Verifier：写出成功条件；准备正确样本和三个错误样本；逐项检查结果；记录失败原因；重复运行；再故意删除测试依赖或修改路径，观察验证器自身错误。
