# Verifier Design：让判定尽量可靠

## 1. Verifier 可以先理解成“判卷程序”

Verifier 会读取任务最后留下的结果，然后给出通过、失败或更细的测试信息。

在不同框架中，Verifier 的目录结构、输出格式和 reward 机制可能不同，所以具体实现要看当前框架文档。这里先学习通用原则。

## 2. 第一原则：和任务说明对齐

如果任务写了 A、B、C，Verifier 最好能检查 A、B、C。

如果 Verifier 额外要求 D，而任务说明从来没提过，就要检查是不是测试越界。

## 3. 尽量检查最终结果，不检查“做题姿势”

优先检查：

- 文件真实内容；
- 程序实际输出；
- 数据结构；
- 状态变化；
- 给定输入下的行为。

少用：

- 源码里有没有某个关键词；
- 是否使用某个固定函数名；
- 是否按照作者预想的命令顺序执行。

除非这些本来就是任务要求。

## 4. Verifier 自己也要测试

至少准备：

1. 一个正确结果，应该通过；
2. 一个缺文件结果，应该失败；
3. 一个内容错误结果，应该失败；
4. 一个边界错误结果，应该失败；
5. 重复运行，结果应该稳定。

如果 Verifier 自己依赖缺失，也应该把它识别成验证器错误，而不是直接说 Agent 失败。

## 5. 为什么隐藏答案和测试隔离很重要

如果 Agent 能直接看到参考答案，或者可以随意改测试文件，那么最后的“通过”就失去意义。

具体怎样隔离取决于评测框架，但原则很简单：

> Agent 应该解决任务，而不是修改判卷规则。

## 6. 常见问题

| 问题 | 后果 |
|---|---|
| 只检查文件存在 | 空文件也可能通过 |
| 只查关键词 | 很容易被表面修改绕过 |
| Test 有隐藏要求 | 合理答案被误判 |
| 依赖随机结果 | 同样输入时判定不稳定 |
| 依赖实时网络 | 外部服务状态影响分数 |
| Agent 能改 Test | 评测结果不可信 |

## 7. 与 Terminal-Bench 的联系

Terminal-Bench 当前公开 task guidelines 强调：任务必须 **verifiable**，并且主要按 **outcome** 判定，而不是按 Agent 的过程打分。

这也是本章最想保留的思路：先定义最终应出现什么结果，再写可靠的检查程序。
