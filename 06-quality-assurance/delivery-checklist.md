# 交付检查清单：从完成任务到可靠交付

## 1. 交付检查的目的

交付质量不只取决于任务是否完成，还取决于交付物是否完整、结构是否正确、运行方式是否清楚，以及结果是否能够被接收方独立检查。

交付检查应将内容质量、工程完整性、验证结果和文件管理纳入统一流程。

## 2. 交付前检查清单

### A. 任务内容

- [ ] 任务目标明确且可判定。
- [ ] 输入、初始状态和预期结果已说明。
- [ ] 约束和资源限制不存在冲突。
- [ ] 任务说明没有关键歧义。
- [ ] 任务要求与测试范围一致。

### B. 文件与目录

- [ ] 必需文件和目录齐全。
- [ ] 文件路径和名称符合约定。
- [ ] 不存在无关临时文件或调试残留。
- [ ] 配置文件格式有效。
- [ ] 文件编码和换行格式符合项目约定。

### C. 环境与执行

- [ ] 镜像可以构建。
- [ ] 依赖版本和安装方式明确。
- [ ] 启动命令可以正常执行。
- [ ] 工作目录、挂载路径和权限正确。
- [ ] 网络及外部依赖已说明。
- [ ] 运行过程不存在未记录的本机隐式依赖。

### D. 测试与验证

- [ ] 测试覆盖关键任务要求。
- [ ] 正确结果能够通过。
- [ ] 关键错误结果能够失败。
- [ ] Verifier 自身可以正常运行。
- [ ] 测试结果稳定且可解释。
- [ ] 失败原因能够区分 Agent、环境和验证器问题。

### E. 交付与安全

- [ ] 交付文件能够正常打开或解压。
- [ ] 交付说明包含必要的运行和验证步骤。
- [ ] 版本号或版本标识清楚。
- [ ] 不包含密码、令牌、个人信息或其他敏感数据。
- [ ] 不包含未经授权的客户数据、内部文档或第三方受限材料。
- [ ] 最终交付包已从干净目录重新检查。

## 3. 交付前的推荐顺序

1. 完成内容和配置修改。
2. 清理临时文件和无关产物。
3. 在干净状态下重新构建环境。
4. 执行任务和验证流程。
5. 检查输出、日志和测试报告。
6. 生成最终交付包。
7. 解压到新目录，检查文件完整性。
8. 记录版本、检查结果和遗留问题。

在最终打包前完成验证，可以减少“本地工作目录可用，但交付包不可用”的情况。

## 4. 交付状态建议

| 状态 | 含义 |
|---|---|
| Ready | 所有阻断项已解决，检查通过 |
| Ready with notes | 核心检查通过，但存在已记录的非阻断事项 |
| Blocked | 存在阻断问题，不应作为完成交付 |
| Rework required | 需要修改后重新执行相关检查 |

状态名称可根据项目约定调整，关键是定义清楚且一致使用。

## 5. 版本与变更记录

每次交付建议记录：

```text
项目 / 任务标识：
版本：
本次变更：
受影响文件：
执行环境：
测试结果：
已知问题：
检查人：
交付日期：
```

不要只依赖压缩包文件名区分版本。版本记录应能说明本次修改了什么，以及哪些检查已重新执行。

## 6. 本章练习

1. 为一个自建任务包填写本清单。
2. 故意在压缩包中加入临时文件，检查能否在交付前发现。
3. 在干净目录中解压最终包，按说明重新运行。
4. 保存验证记录和版本说明。
5. 对未通过项给出明确状态，不要将“部分可用”描述成“全部完成”。

## 7. 公开作品集的额外边界

用于公开 GitHub 作品集时，交付检查还应增加来源与授权检查：

- 仅使用自行编写内容、合成数据或明确允许再分发的公开资料；
- 不上传实习期间的原始任务包、客户要求、内部提示词、测试脚本或执行记录；
- 不复制企业内部验收材料或平台数据；
- 对公开项目的引用保留来源链接，并遵守相应许可证；
- 对个人经历的描述准确区分本人工作、AI 辅助和团队成果。
