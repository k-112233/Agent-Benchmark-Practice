# Delivery Checklist：提交之前最后检查一遍

## 1. 为什么需要最后检查

很多问题不是代码逻辑错，而是提交时漏文件、混进临时文件、运行说明不完整，或者本机能跑但换目录就不能跑。

所以最后交付前最好单独做一次检查，而不是默认“刚刚测试通过就一定没问题”。

## 2. 内容

- [ ] Task 目标明确；
- [ ] 输入和输出位置清楚；
- [ ] 约束没有互相冲突；
- [ ] 关键要求都有对应检查；
- [ ] 没有明显歧义。

## 3. 文件

- [ ] 必需文件齐全；
- [ ] 路径和文件名正确；
- [ ] 没有调试残留、缓存和临时文件；
- [ ] 配置文件可以正常解析；
- [ ] README 中的命令和实际路径一致。

## 4. 环境

- [ ] 镜像可以构建；
- [ ] 依赖版本明确；
- [ ] 启动命令可以执行；
- [ ] 权限和挂载路径正确；
- [ ] 网络依赖已经说明；
- [ ] 没有依赖“只有我电脑上才有”的配置。

## 5. 测试

- [ ] 正确结果能通过；
- [ ] 典型错误结果能失败；
- [ ] Test / Verifier 自己可以正常运行；
- [ ] 重复运行结果稳定；
- [ ] timeout 和 error 没被误记成普通失败。

## 6. 公开 GitHub 还要额外看什么

- [ ] 没有 `.env`、API Key、Token 或密码；
- [ ] 没有个人隐私数据；
- [ ] 没有来源不清或无权再分发的文件；
- [ ] 引用公开项目时保留来源；
- [ ] `.gitignore` 能过滤缓存、压缩包和本地临时文件；
- [ ] Git 历史里也没有曾经提交过的敏感内容。

这里不需要写大量“免责声明”，真正重要的是检查仓库里实际有什么。

## 7. 本仓库发布前的命令

```powershell
python .\scripts\project_audit.py
```

然后再看：

```powershell
git status
git diff --cached
```

确认准备提交的文件就是自己打算公开的内容。

## 8. 版本记录保持简单即可

如果项目继续更新，可以记录：

```text
版本：
主要修改：
测试结果：
已知问题：
日期：
```

Git commit 本身也能承担一部分版本记录作用，所以没必要重复维护过多表格。
