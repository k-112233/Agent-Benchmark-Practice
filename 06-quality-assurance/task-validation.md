# Task Validation：发布或评测前先把任务自己跑通

## 1. 为什么要验证 Task 本身

任务说明写得不错，不代表任务一定能运行。常见问题还有：

- 缺文件；
- Docker 构建失败；
- 路径错误；
- 依赖版本不对；
- Verifier 自己有 bug；
- 成功条件实际上无法达到。

所以 Task Validation 不只是文字校对，而是从头到尾把任务检查一遍。

## 2. 可以按五部分检查

### 任务说明

确认目标、输入、输出、限制和成功标准都能看懂。

### 文件结构

确认必需文件存在，路径和命名一致，没有多余临时文件。

### 环境

确认 Dockerfile、依赖、工作目录、权限和网络条件能正常工作。

### 可行性

用自己确认过的正确操作或参考解法，验证任务确实能完成。

### Verifier

至少测试：

1. 正确结果能通过；
2. 典型错误结果不能通过；
3. Verifier 自己出错时能够区分出来。

## 3. 一个实用顺序

```text
静态检查
  ↓
构建环境
  ↓
启动环境
  ↓
验证任务可解
  ↓
检查 Verifier
  ↓
恢复干净状态再跑一次
```

这个顺序的好处是，前面发现结构问题时不用浪费时间跑后面的长流程。

## 4. 缺陷可以简单分级

| 级别 | 例子 |
|---|---|
| Blocker | 环境起不来、Task 无解、Verifier 不能运行 |
| Major | 关键要求有歧义、关键结果没有测试 |
| Minor | 文档或命名问题，不影响主要结果 |
| Improvement | 当前可用，但以后可以做得更清楚 |

分级看“对评测可信度的影响”，而不是看修起来麻不麻烦。

## 6. 和本仓库工具的关系

`tools/task-package-checker/` 只覆盖“静态检查”的一小部分：它能找缺文件和元数据错误，但不会替你构建 Docker，也不会真正执行 Task。

这也是为什么静态检查通过之后还需要运行测试和环境验证。
