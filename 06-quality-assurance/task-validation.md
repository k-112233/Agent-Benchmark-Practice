# 任务验证：确认任务本身可执行、可理解、可判定

## 1. 为什么需要任务验证

任务验证（Task Validation）发生在任务交付或正式评测之前，目的是确认任务包具备基本的可执行性、完整性和可评价性。

一个任务即使描述清楚，也可能因为文件缺失、环境构建失败、依赖不完整或验证器错误而无法正常评测。因此，任务验证不能只做文字校对，还应覆盖任务说明、文件结构、运行环境、执行流程和验证逻辑。

## 2. 任务验证的主要维度

### 2.1 任务说明检查

重点检查：

- 目标是否明确，是否能判断完成状态；
- 输入、初始状态和预期输出是否交代清楚；
- 操作限制和资源约束是否明确；
- 是否存在互相冲突的要求；
- 是否包含无法验证或含义模糊的表述；
- 任务是否意外依赖未声明的背景知识。

### 2.2 文件结构检查

检查任务要求的文件是否齐全、路径是否正确、文件命名是否一致，以及是否存在无关文件或意外残留。

文件结构应与所使用的评测框架规范一致。不要把本仓库中的练习结构当作所有框架的强制标准。

### 2.3 环境构建检查

确认基础镜像、依赖、启动脚本和必要配置可以正常使用。重点检查：

- Dockerfile 是否能成功构建；
- 依赖是否能在目标环境中安装；
- 工作目录和文件路径是否正确；
- 运行时权限是否满足任务要求；
- 网络和外部服务依赖是否已说明。

### 2.4 任务执行检查

使用明确的初始状态启动任务，确认执行流程能够开始，任务说明没有明显遗漏，并且任务目标在给定限制下具有可行性。

如果使用参考解法进行验证，应将其作为可行性检查，不要把参考解法本身泄露给评测中的 Agent。

### 2.5 Verifier 检查

至少验证三类情况：

1. 正确结果能够通过；
2. 关键错误结果能够失败；
3. 测试依赖或测试环境异常时，能够识别为验证器问题，而不是简单记为 Agent 失败。

## 3. 任务验证流程

建议按以下顺序执行：

1. **静态检查**：检查任务说明、文件名、目录结构和配置。
2. **构建检查**：构建所需镜像，确认依赖和配置有效。
3. **启动检查**：按正式运行方式启动环境。
4. **可行性检查**：确认任务目标在给定条件下可以完成。
5. **验证器检查**：使用正向、负向样本检查判定逻辑。
6. **干净状态复测**：重置初始状态后重新运行，排除残留影响。
7. **记录结果**：保存检查项、结果、异常和修复记录。

## 4. 缺陷分级

| 级别 | 定义 | 处理原则 |
|---|---|---|
| 阻断问题 | 无法构建、启动或验证，或任务目标不可实现 | 修复后重新验证 |
| 重要问题 | 任务要求存在明显歧义，或关键要求缺少有效测试 | 修复并进行针对性复测 |
| 一般问题 | 文档表达、命名或非关键配置不规范 | 记录并在交付前处理 |
| 建议改进 | 不影响当前有效性，但可提升可维护性 | 纳入后续优化 |

分级应依据对任务有效性和评测可信度的影响，不应仅按修改工作量判断。

## 6. 本章练习

创建一个自建的最小任务包，完成以下操作：

1. 检查任务说明是否能转化为明确的成功条件。
2. 检查文件和目录是否齐全。
3. 构建并启动运行环境。
4. 使用参考操作确认任务可行。
5. 使用正确和错误结果验证测试逻辑。
6. 删除一个必要文件，观察静态检查能否发现。
7. 故意修改一个依赖版本，观察构建或运行阶段的错误。
8. 根据缺陷分级填写验证记录。
